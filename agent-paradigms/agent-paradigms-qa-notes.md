# Agent Paradigms QA Notes

## 原问题

### 1) 动态重规划机制

Plan-and-Solve 范式将任务分解为“规划”和“执行”两个阶段。  
在 4.3 节的实现中，规划阶段生成的计划是“静态”的（一次性生成，不可修改）。如果在执行过程中发现某个步骤无法完成或结果不符合预期，应该如何设计一个“动态重规划”机制？

### 2) Plan-and-Solve 与 ReAct 对比

对比 Plan-and-Solve 与 ReAct：在处理“预订一次从北京到上海的商务旅行（包括机票、酒店、租车）”这样的任务时，哪种范式更合适？为什么？

### 3) 分层规划系统设计

尝试设计一个“分层规划”系统：先生成高层次的抽象计划，然后针对每个高层步骤再生成详细的子计划。这种设计有什么优势？

---

## 对应解答

### 问题拆解与回答思路

这个问题本质上分为三个层面：

- 机制层：静态 Plan-and-Solve 如何升级为执行中可修正的动态规划系统。
- 范式选择层：Plan-and-Solve vs ReAct 在多工具、强不确定任务中的适配性。
- 架构层：分层规划（高层计划 + 子计划）的工程价值。

---

### 1) 静态计划如何升级为“动态重规划”

静态计划的关键缺陷是：假设环境稳定。现实中会出现库存变化、接口失败、预算冲突、时间冲突等问题。  
因此需要建立“监控-诊断-重规划-恢复执行”的闭环，而不是失败后全盘重来。

#### 推荐闭环：Monitor -> Diagnose -> Replan -> Resume

- Monitor（执行监控）
  - 每步记录输入、输出、耗时、成功/失败、置信度、约束满足状态。
  - 给每步定义完成标准（Definition of Done）。
- Diagnose（失败诊断）
  - 可重试失败：超时、限流、短期抖动。
  - 策略失败：步骤方法不合理。
  - 约束冲突：预算/时间/偏好不兼容。
- Trigger（重规划触发）
  - 连续 N 次失败。
  - 关键约束破坏（如预算超限）。
  - 下游依赖被破坏（如航班变化导致酒店不匹配）。
- Replan Scope（重规划粒度）
  - 优先局部重规划，只重算受影响步骤。
  - 全局约束变化才触发全局重规划。
- Versioning（计划版本化）
  - Plan v1 -> v2 -> v3，记录变更原因和差异。
- Compensation（补偿机制）
  - 已产生副作用的步骤（如下单）支持取消与回滚。
- Guardrail（终止与降级）
  - 限制最大重规划次数、时间预算、成本预算。
  - 超限后输出候选方案并请求用户确认。

#### 最小状态模型建议

- Goal：目标与硬/软约束
- Plan：步骤图（依赖、前置条件、完成条件）
- ExecutionState：步骤状态机
- WorldState：外部工具事实快照
- Policy：重试/重规划/终止策略

---

### 2) Plan-and-Solve 与 ReAct：商务旅行预订场景

任务特征：多子任务、多系统、多约束、强实时变化。

#### 结论

- 纯静态 Plan-and-Solve：不够稳（对动态变化响应弱）。
- 纯 ReAct：全局一致性偏弱（容易局部贪心）。
- 最优实践：混合范式  
  - 高层：Plan-and-Solve 负责全局约束和总体路径  
  - 低层：ReAct 负责具体工具调用与异常适配  
  - 中间：动态重规划机制持续纠偏

#### 对比维度

- 全局一致性：Plan-and-Solve 更强
- 环境适应性：ReAct 更强
- 执行效率：Plan-and-Solve 减少盲调，ReAct 处理异常更灵活
- 可解释性：Plan-and-Solve 更易审计，ReAct 更过程化

---

### 3) 分层规划系统设计与优势

#### 分层结构

- L0 目标层：定义任务目标、硬约束、软约束
- L1 高层计划层：抽象步骤（如机票 -> 酒店 -> 租车 -> 校验 -> 确认）
- L2 子计划层：为每个高层步骤展开详细执行策略
- L3 执行层：具体工具调用与参数执行
- 反馈层：执行监控、失败诊断、局部重规划

#### 优势

- 复杂度隔离：高层关注“做什么”，低层关注“怎么做”
- 局部修复：失败时只重算子计划，减少全局震荡
- 并行能力：独立子计划可并发执行
- 可复用：子计划模板可跨任务复用
- 可观测：每层可定义指标（成功率、重试率、成本偏差）
- 易协同：高层计划可供人工审阅，低层自动化执行

---

## 总结（直接结论）

- 动态重规划的核心是“执行反馈闭环 + 局部重规划 + 版本化 + 补偿机制”。
- 对商务旅行预订这类高不确定任务，混合范式（高层 Plan-and-Solve + 低层 ReAct）更合适。
- 分层规划是从 demo 走向生产系统的关键工程设计，能显著提升可维护性、扩展性和鲁棒性。

## ReAct 添加 Calculator：问题与解答整理

### 原问题 A：为什么 ReAct 解析不出 Thought 和 Action？

#### 现象

- 模型已返回内容，但流程打印“未能解析出有效 Action”并终止。

#### 原因分析

- 解析正则对格式较敏感，依赖精确标签与结构：
  - `Thought:`
  - `Action:`
  - `ToolName[tool_input]`
- 模型若出现轻微漂移（大小写、空格、全角冒号、附加解释文本等），就可能匹配失败。

#### 处理建议

- 在解析前输出原始 `response_text`（可用 `repr`）检查真实格式。
- 为格式错误增加明确反馈，写入历史，让模型下一轮纠正格式。
- 保持 Prompt 协议清晰，并在失败时给具体纠偏指令。

---

### 原问题 B：`Finish[...]` 分支为什么会报 `NoneType has no attribute group`？

#### 现象

- 执行到 `re.match(...).group(1)` 时崩溃。

#### 根因

- 模型输出 `Action: Finish[...]` 时，可能漏掉结尾 `]` 或有额外尾部文本；
- `re.match` 返回 `None`，继续 `.group(1)` 直接抛异常。

#### 修复思路

- 先判空再提取，不直接链式 `.group(1)`。
- 优先严格匹配，失败时做有限容错：
  - 严格：`Finish\[(.*)\]\s*$`
  - 容错：若仅检测到 `Finish[` 前缀，则提取剩余文本
  - 否则判定格式无效并终止

---

### 原问题 C：如何增加“工具选择失败”的纠偏机制？

#### 目标

- 当模型连续调用错误工具或给出错误参数时，不是直接死循环，而是能被系统引导纠正。

#### 已采用机制

- 失败事件写入 `history`，并附上结构化 `ToolFeedback`：
  - 失败原因（格式错误/工具不存在/工具执行失败）
  - 可用工具提示
  - 下一步修正建议（例如计算题优先 `Calculator`）
- 维护连续失败计数（例如 3 次）：
  - 达到阈值后终止，防止无效循环
- 一旦成功执行工具，清理近期失败反馈，避免历史噪声干扰

#### 工程价值

- 提高自纠错能力
- 降低无效 token 消耗
- 让失败行为可观测、可调参

---

### 原问题 D：如何添加 Calculator 工具并保证安全？

#### 实现要点

- 基于 `ast.parse(..., mode="eval")` 解析表达式
- 仅允许白名单节点和运算符：
  - 二元：`+ - * / // % **`
  - 一元：正负号
- 支持中文符号归一化：
  - `× -> *`
  - `÷ -> /`
- 明确错误处理：
  - 空输入
  - 除零
  - 非法表达式/不支持节点

#### 为什么不用 `eval`

- `eval` 有安全风险，可能执行非预期代码；
- AST 白名单更符合工具执行安全边界。

---

### 原问题 E：没有理解 ToolExecutor 的工具挑选逻辑

#### 当前选择流程

1. 注册工具时保存：`description`、`func`、`keywords`
2. 对用户问题做 token 化（中英文词元）
3. 对每个工具打分：
   - 关键词命中加高权重（示例中为 +3）
   - 描述命中加低权重（示例中为 +1）
4. 按分数降序取 Top-K（如 8 个）
5. 若无命中，回退到前 N 个工具

#### 作用

- 避免把所有工具都塞进 Prompt，降低噪声
- 在工具规模增大时减少上下文成本

#### 已知限制

- 当前是关键词/子串匹配，不是语义级检索；
- 后续可升级为 embedding 检索 + rerank + schema 校验。

---

### 这一组改动的阶段性结论

- ReAct 在加入 Calculator 后，具备了数学计算能力；
- 加入失败纠偏后，工具调用链路更稳健、可恢复；
- 引入 Top-K 工具筛选后，为 50/100 工具规模演进打下基础。

## Reflection 机制：问题与解答整理

### 原问题 1：执行和反思使用不同模型会有什么影响？

问题背景：在 4.4 节代码生成案例中，执行与反思阶段使用同一个模型。若改为“双模型”（快模型执行、强模型反思），会产生什么影响？

#### 结论

- 这是一个典型的“成本-质量-时延”优化手段，通常是可取的。
- 推荐模式：`快速模型负责生成`，`强模型负责批判与策略修正`。

#### 正面影响

- 成本优化：大部分 token 消耗在执行阶段，快模型可显著降成本。
- 吞吐提升：初稿生成更快，整体迭代周期缩短。
- 反思质量提升：强模型更擅长发现深层缺陷（算法复杂度、边界条件、论证漏洞）。
- 角色分工清晰：执行模型偏“产出”，反思模型偏“评审/裁判”。

#### 潜在风险

- 风格漂移：两模型偏好不同，可能导致“改一轮变一个写法”。
- 目标错位：反思模型给出过高标准，执行模型无法稳定落地。
- 循环震荡：强模型不断提出新问题，快模型修不干净，迭代变长。
- 上下文不一致：若反思提示不结构化，执行模型难以准确吸收反馈。

#### 工程建议

- 固定接口协议：反馈采用结构化格式（问题类型、严重级别、建议改法、验证标准）。
- 约束改写范围：执行阶段按“最小必要改动”修复，避免大幅重写。
- 引入质量门槛：仅当关键指标未达标才进入下一轮反思。
- 做 A/B 评估：比较“单模型 vs 双模型”的质量、时延、成本曲线。

### 原问题 2：当前终止条件是否合理？如何更智能？

现有终止条件：

- 反馈包含“无需改进”
- 或达到最大迭代次数

#### 评价

- 合理但偏粗糙：实现简单、可控，但对真实质量提升不够敏感。
- 主要问题：依赖文本关键词，容易误判；无法区分“关键问题未解”与“小问题可接受”。

#### 更智能的终止机制（建议）

采用“多信号终止”而非单一条件：

1. 质量分数阈值（Quality Score）
   - 设定综合评分（如正确性、鲁棒性、可读性、规范性）。
   - 当分数 >= 阈值且关键维度不低于底线时终止。

2. 边际收益终止（Diminishing Returns）
   - 连续两轮提升幅度低于最小增益（如 < 1%）时终止。

3. 关键缺陷清零（Critical Defects）
   - 高严重级别问题（P0/P1）全部关闭后，才允许结束。

4. 一致性校验
   - 反思结论与自动评测（测试、lint、规则检查）一致时才终止。

5. 预算约束
   - 达到时间/token/成本预算上限时触发“受控收敛”，输出当前最优版本并标注遗留风险。

可组合成终止规则：

- `(质量达标 AND 关键问题清零 AND 增益趋缓) OR 预算耗尽`

### 原问题 3：学术论文写作助手的多维 Reflection 机制如何设计？

目标：生成论文初稿后，围绕多个维度持续反思并优化，而不是只做语言润色。

#### 一、总体架构

- Drafter（初稿生成器）
- Multi-Critic 评审器（多维反思）
- Refiner（定向改写器）
- Verifier（规范与一致性校验）
- Memory（版本与问题追踪）

循环：`生成 -> 多维评审 -> 定向修订 -> 自动校验 -> 是否终止`

#### 二、多维反思维度与检查点

1. 段落逻辑性（结构维度）
   - 检查论点链条是否完整（问题-方法-结果-结论）。
   - 检查段落过渡、前后因果、是否有跳跃论证。
   - 输出：逻辑断点清单 + 建议重排方案。

2. 方法创新性（学术贡献维度）
   - 提炼“贡献声明”是否清晰、可验证。
   - 比对相关工作差异点是否具体（非口号式创新）。
   - 输出：创新点强度评分 + 需要补证的论据清单。

3. 语言表达（可读性维度）
   - 检查术语一致性、句法冗余、歧义表达、学术语气。
   - 输出：逐段改写建议（保留原意，减少空泛句）。

4. 引用规范（合规维度）
   - 检查引用是否覆盖关键主张，是否存在“无引文结论”。
   - 检查引用格式与目标模板（APA/IEEE/ACL）一致性。
   - 检查引用与参考文献一一对应，避免幽灵引用。

5. 实验与可复现性（可信度维度）
   - 检查实验设置、数据划分、评价指标、统计显著性是否齐全。
   - 检查是否给出复现实验细节（超参数、环境、代码入口）。

#### 三、反思输出协议（建议）

每轮反思统一输出结构：

- `dimension`: 维度名
- `severity`: 严重级别（critical/major/minor）
- `issue`: 问题描述
- `evidence`: 文中证据位置
- `suggestion`: 可执行修改建议
- `acceptance_criteria`: 修改完成判据

这样 Refiner 可以做“定向修复”，避免全文重写。

#### 四、改写策略

- 先修 `critical`，再修 `major`，最后 `minor`。
- 单轮只改一个或少量维度，防止改动互相覆盖。
- 每轮保留 diff 与变更原因，保证可追踪与可回滚。

#### 五、终止策略（论文场景）

- 维度分数全部达标（如每维 >= 80）
- 且 `critical = 0`
- 且连续两轮无实质提升
- 或达到预算上限后输出“当前最佳稿 + 待完善清单”

---

### 本组问题的总结

- 双模型 Reflection 往往能提升性价比，但必须通过结构化反馈协议控制风格漂移和循环震荡。
- 终止条件应从“关键词触发”升级为“多信号决策”，兼顾质量、收益与成本。
- 学术写作助手应采用多维评审器，围绕逻辑、创新、表达、引用、复现性等维度进行可执行优化，才能持续提升论文质量。

## 提示词工程：问题与解答整理

### 原问题 1：ReAct 与 Plan-and-Solve 提示词结构差异如何服务各自范式？

#### 结构差异

1. ReAct（4.2.3）
   - 强约束输出协议：`Thought:` + `Action:`
   - `Action` 必须是工具调用或 `Finish[...]`
   - 持续引入 `History`，每轮根据观察再决策

2. Plan-and-Solve（4.3.2）
   - 先由 Planner 输出可解析的完整计划（Python 列表）
   - 再由 Executor 逐步执行“当前步骤”
   - 执行提示词强调“只回答当前步骤”，减少跨步干扰

#### 为什么这样设计

- ReAct 的核心逻辑是“推理-行动-观察”循环，所以提示词把“动作语法”和“历史反馈”放在中心位置，服务在线决策与纠错。
- Plan-and-Solve 的核心逻辑是“先分解再求解”，所以提示词将“结构化计划”与“分步执行”拆成两个角色，服务全局一致性与可控执行。

#### 工程启示

- ReAct 更依赖格式遵循率与工具协议稳定性。
- Plan-and-Solve 更依赖计划质量与计划解析鲁棒性。
- 不确定性高、外部变化频繁时 ReAct 更灵活；任务结构稳定时 Plan-and-Solve 更可控。

### 原问题 2：修改 Reflection 角色设定后输出变化如何？

我基于同一任务和同一代码做了角色对比实验：

- 角色 A：`你是一位极其严格的代码评审专家和资深算法工程师`
- 角色 B：`你是一位注重代码可读性的开源项目维护者`

#### 实验观察

1. 严格评审专家角色（A）
   - 反馈聚焦复杂度、性能瓶颈与算法替代（如筛法、分段筛）
   - 结论更“性能导向”，几乎不关注注释/命名/文档风格

2. 开源维护者角色（B）
   - 反馈覆盖可读性、类型注解、边界处理、测试与文档
   - 输出结构更接近工程 code review checklist

#### 结论

- 角色设定不是“文风修饰”，而是直接改变模型的优化目标和注意力权重。
- 在 Reflection 中，角色提示等价于“评审维度配置”：
  - 算法专家：性能与复杂度优先
  - 维护者：可读性、稳定性、可维护性优先

### 原问题 3：为本章智能体加入 few-shot 并对比效果

我以 ReAct 智能体做了小样本实验（同一任务，3 轮对比）：

- 任务：`计算 (123 + 456) × 789 / 12 = ?`
- 指标：是否符合 `Thought + Action` 且 `Action` 满足 `ToolName[...]` 语法

#### 实验设置

- 无 few-shot：仅给输出协议
- 有 few-shot：增加 1 条标准示例  
  `Question -> Thought -> Action: Calculator[...]`

#### 实验结果（可复现样本）

- 无 few-shot：`0/3`（3 次都返回空响应）
- 有 few-shot：`3/3`（3 次都严格输出 Thought/Action 且调用 Calculator）

#### 分析

- few-shot 显著提升了格式对齐与动作可解析性，尤其在模型偶发空响应或协议漂移时有明显稳定作用。
- 但 few-shot 也可能带来“示例迁移副作用”：模型过度模仿示例表达，导致任务语义多样性下降。

#### 实践建议

- few-shot 示例要短小、单一目标、强约束（仅演示协议，不夹带无关知识）。
- 示例与真实任务之间加显式分隔（如“现在处理真实任务”），降低示例污染。
- 评估时至少同时看两个指标：
  1) 协议遵循率（格式正确）
  2) 任务完成率（答案正确）

---

### 本组问题总结

- ReAct 与 Plan-and-Solve 的提示词差异，本质是为各自执行范式服务：前者服务在线决策闭环，后者服务离线分解与分步执行。
- Reflection 的角色设定直接决定“模型关注什么”，应把角色当作评审策略开关来设计。
- few-shot 是提升格式遵循率的高杠杆手段，但要配合任务分隔与双指标评估，避免“只对齐格式，不对齐任务”。

## 客服智能体架构设计：问题与解答整理

### 原问题

某电商初创公司希望使用“客服智能体”替代部分真人客服，实现降本增效。能力要求：

- 理解用户退款申请理由
- 查询订单信息与物流状态
- 根据公司政策判断是否批准退款
- 生成并发送得体的回复邮件
- 当置信度低于阈值时，进行自我反思并给出更审慎建议

作为产品负责人，需要回答：

1. 选择哪种范式（或组合）作为核心架构？
2. 系统需要哪些工具（至少 3 个）？
3. 如何设计提示词，兼顾公司利益与用户友好？
4. 上线后有哪些风险与挑战？如何通过技术手段降低风险？

### 解答

#### 1) 核心架构范式选择

推荐组合：`Plan-and-Solve + ReAct + Reflection`

- Plan-and-Solve：负责“受理 -> 核验 -> 决策 -> 回信 -> 记录”的主流程编排，保证可审计和可控性。
- ReAct：负责执行阶段的工具调用与动态调整（订单/物流查询、异常处理）。
- Reflection：在低置信、规则冲突、证据不足时触发二次审查，给出更谨慎结论或转人工。

这种组合同时兼顾流程稳定性、执行灵活性与风险兜底能力。

#### 2) 工具设计（至少 3 个）

可用工具示例：

1. `OrderQueryTool`
   - 功能：按 `user_id/order_id` 查询订单详情（金额、商品、支付、签收、历史退款等）。

2. `LogisticsStatusTool`
   - 功能：查询物流轨迹、签收状态、异常节点（延迟、丢件、拒收等）。

3. `PolicyEngineTool`
   - 功能：根据公司退款规则输出 `approve/reject/manual_review`，并返回命中规则与置信度。

4. `EmailComposerSenderTool`
   - 功能：根据决策结果生成并发送邮件，支持草稿模式、审核模式与发送回执。

5. `RiskScoringTool`（可选）
   - 功能：对高风险退款行为打分，识别潜在欺诈或滥用。

#### 3) 提示词设计（兼顾公司利益与用户友好）

建议采用分层提示词：

- 系统层（不可变原则）
  - 严格遵守公司政策与合规要求，不可编造事实；
  - 决策必须基于工具返回证据；
  - 低置信场景必须触发反思或人工升级。

- 决策层（结构化输出）
  - 输出字段建议：`decision`、`confidence`、`policy_hits`、`evidence`、`next_action`；
  - 优先结构化（JSON）以便程序校验和审计。

- 沟通层（回复语气）
  - 先给结论，再给依据，再给可执行下一步；
  - 语气专业、礼貌、同理，避免对抗式措辞；
  - 对拒绝结果提供清晰补充材料路径和申诉渠道。

#### 4) 风险与挑战，以及技术缓解

主要风险：

- 误判退款（误拒伤害体验、误批导致损失）
- 幻觉与编造（杜撰物流/政策依据）
- 数据与隐私风险（PII 泄露、越权访问）
- 策略漂移（同类案件判定不一致）
- 对抗输入（诱导绕过策略）

缓解手段：

- 规则引擎兜底：关键决策由 `PolicyEngine` 主导，LLM 负责解释与沟通；
- 工具证据强约束：无证据不得下最终结论；
- 结构化输出校验：JSON Schema + 自动重试；
- 置信度门控：低于阈值自动转人工；
- 审计日志全链路：输入、工具结果、规则命中、最终决策全记录；
- 安全策略：最小权限、脱敏、敏感操作二次确认；
- 监控评估：误拒率、误批率、人工接管率、客服满意度、平均处理时长持续追踪。

### 本组问题总结

- 对客服退款场景，单一范式不够，推荐“流程编排 + 工具执行 + 反思兜底”的组合架构。
- 工具设计应覆盖“事实获取、规则决策、用户沟通、风控评估”四类核心能力。
- 通过分层提示词和结构化输出，可以在“公司利益”和“用户体验”之间建立可控平衡。
- 上线可用性的关键不只是模型能力，更在于规则约束、审计能力与风险监控体系。
